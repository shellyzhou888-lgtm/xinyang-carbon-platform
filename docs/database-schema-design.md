## 1. 先讲理念：数据湖 + 数据仓库，“结构先行、数据慢慢填”

老师说的“先构建结构，后续慢慢填”是对的，前提是结构要按**数据湖 + 数据仓库**的思路设计，而不是为每张 Excel 表各建一张表。

| | 数据湖（本库的 `raw`） | 数据仓库（本库的 `core` + `fact`） |
| --- | --- | --- |
| 存什么 | 原始文件、表格行、接口报文，**原样保存** | 清洗后、口径统一、可以直接计算的数据 |
| 结构 | 宽松：一行原始数据存成一个 JSON | 严格：字段、单位、约束都定好 |
| 什么时候定义结构 | 读取时（schema-on-read） | 写入时（schema-on-write） |
| 好处 | 来什么都能先收下，不会因为格式不对而丢数据 | 计算可靠，页面和 Agent 查询简单 |

本项目的数据流：

```text
用户上传 Excel / 手工填报 / 接口推送 / AI 估值
   │
   ▼
raw.document（文件） → raw.import_batch（批次） → raw.import_record（每行原样存 JSON）
   │  按 core.import_template + core.import_field_map 配置的映射解析
   ▼
fact.energy_activity / fact.statistic_value …（带来源和质量标记）
   │  公式（core.formula，人工审核后才生效）
   ▼
fact.indicator_value → mart 视图 → 网站页面、Agent
```

### 为什么以后加数据不需要大改结构

通用结构的关键是“**长表 + 字典**”：新增一类数据，只是在字典里加一行，而不是给表加一列。

| 以后遇到的情况 | 处理方式 | 是否需要改表结构 |
| --- | --- | --- |
| 新增一种能源（如氢能） | `core.energy_type` 加一行，`core.factor` 加因子 | 否 |
| 新增一种统计量（如中水回用量） | `core.metric_def` 加一行，数据写进 `fact.statistic_value` | 否 |
| 新增或修改评价标准、指标、分值 | `core.standard_version`、`core.indicator_def` 加行或改行 | 否 |
| 园区给了一张新格式的 Excel | `core.import_template` 加一个模板、配置字段映射 | 否 |
| 暂时看不懂、还没想好怎么用的数据 | 用 `raw_only` 模板只入湖，原样保留，以后再解析 | 否 |
| 企业多了一些预料外的属性 | 写进 `attributes`（JSON）扩展列 | 否 |
| 确实需要一张全新结构的表 | 由 `green_ddl` 在 `lab` schema 自建 | 只新增表，不改已有表 |

> 需要注意：数据湖不是“什么都往里扔”。每个批次都要记录来源、上传人、对应模板，否则会变成没人看得懂的“数据沼泽”。`raw.import_batch` 就是为此设计的。

## 2. 角色与权限

权限挂在不能登录的**组角色**上，登录账号加入组角色即可获得权限。数据库里没有为新角色设置任何密码。

| 角色 | 能做什么 | 不能做什么 | 当前成员 |
| --- | --- | --- | --- |
| `postgres` | 全部（人工管理员） | — | 人工执行迁移、建角色、备份 |
| `greensystem` | 拥有正式表；迁移文件以它的身份建表 | — | 迁移时由 `postgres` 切换为此身份 |
| `green_ddl` | **建表**（core、raw、fact、mart、lab）；修改自己建的表；读写业务数据 | 删除表、列、视图、schema；DELETE、TRUNCATE；修改迁移管理的正式表结构 | `zyz`（登录后自动切换为此身份） |
| `green_app` | 读写业务数据（无删除） | 建表、删除 | `zyz`（经由 green_ddl 继承） |
| `green_etl` | 读 core；写 raw、fact、lab | 建表、删除 | 暂无 |
| `green_agent_ro` | 读 core（字典、指标、术语）、读 mart 视图 | 读 raw、fact；任何写操作 | 暂无 |

### 为什么这样分

- **为什么 `green_app` 不能建表**：`green_app` 是网站服务端日常运行用的账号，处理所有用户请求。如果它能执行 DDL，一旦网站有 SQL 注入之类的漏洞，攻击者就能改动库结构。所以建表权限单独放在 `green_ddl` 上，只给需要建表的账号（数据库管理 Agent、开发账号）。开发期 `zyz` 两个身份都有，正式上线时建议拆成两个登录账号。
- **为什么只读 Agent 原来读不了 core，现在开放了**：原设计让 Agent 只走 mart 视图，接口最小。考虑到 core 里只有字典、指标定义、术语，没有敏感数据，而 Agent 解释指标时需要它，所以 0002 开放了 core 只读。raw（原始文件、发票）和 fact（未经筛选的明细，含已作废的版本）仍不开放，Agent 查数据统一走 mart 视图，保证查到的都是当前有效数据。
- **“能建表但不能删”的实现方式**：
  - 删表、删列：由事件触发器 `green_block_drop` 统一拦截，非超级用户执行时会报错，整条语句回滚。
  - 删数据：`green_ddl` 自建的表默认收回了 DELETE、TRUNCATE 权限。
  - 修改数据：用新行替换旧行，旧行标记 `is_current = false`，历史可追溯。

### 实测结果（2026-10-20，以 `zyz` 实际登录）

| 操作 | 结果 |

### 区间值不替你选

标准只给区间的因子，只录了区间，**没有填采用值**，需要按实测热值或统一口径确定后再填：
- 天然气折标 1.1000~1.3300 kgce/m³，热值 32238~38979 kJ/m³。
- 沼气折标 0.7143~0.8286 kgce/m³。

### 审核方法

因子和公式经审核后才参与计算。审核通过一条因子的示例：

```sql
UPDATE core.factor
SET status = 'approved', approved_by = '审核人姓名', approved_at = now()
WHERE factor_id = 1;
```

公式同理，更新 `core.formula` 的 `status`、`reviewed_by`、`reviewed_at`。所有改动都会被 `audit.change_log` 自动记录。后台页面做好后，可以在页面上逐条审核。

## 5. 关键设计说明

- **对象树**：`org_node.path` 以 `node_id` 为标签，由触发器维护，移动节点时下级路径自动更新。汇总某片区时用 `path <@ '1.3'` 查出整棵子树。
- **碳核算口径**（910 号附件 4）：
  - 园区排放 = 燃料燃烧 + 加工转换 + 电力净受入 + 热力净受入 + 工业过程。
  - 送出的电力、热力在 `carbon_emission` 中记为负值。
  - 用作原料的能源（`use_type = raw_material`）计入综合能耗，但不计燃烧排放。
- **2026 版分值**：暂按 2025 版对应指标配置；新增的第 14、18 项分值为空，官方公布后在 `indicator_def.score` 中补上即可。
- **前台只展示达标指标**：由 `mart.v_indicator_display` 过滤（当前有效、已达标、允许展示）。
- **迁移执行**：用 `scripts/apply-migrations.ps1`（先加 `-DryRun` 试跑）。psql 在含中文的路径下打不开文件，所以脚本通过标准输入传 SQL。

## 7. 因子复核：电网电力、天然气、热力、柴油（2026-10-20）

### 7.1 为什么加“口径”（variant）

同一能源可能并存多个合法因子。例如电网电力，零碳园区核算按 910 号文用全国化石能源电力因子，绿色园区评价用省级电力平均因子更贴近实际。如果表里只能存一个值，就得来回改，历史结果无法复现。迁移 0009 做了三件事：

- 因子表加 `variant` 列，同一能源、同一年份可并存多个口径。
- 标准版本加 `factor_preferences`，指定该标准计算时用哪个口径。
- 因子表加 `reviewed_by / reviewed_at / review_note`。“复核”表示已对照原文核对数值；“批准”（`approved`）仍由负责人确认后才参与计算。

### 7.2 复核结果

官方原文已下载归档到 `policies/factors/`。

**电网电力**（kgCO₂/kWh，生态环境部、国家统计局公告）

| 年份 | 公告 | 全国平均 | 华中 | 河南 | 全国（不含市场化非化石） | 全国化石能源电力 |
| --- | --- | --- | --- | --- | --- | --- |
| 2021 | 2024 年第 12 号 | 0.5568 | 0.5354 | **0.6369** | 0.5942 | 0.8426 |
| 2022 | 2024 年第 33 号 | 0.5366 | 0.5395 | **0.6058** | 0.5856 | **0.8325** |
| 2023 | 2025 年第 47 号 | 0.5306 | 0.5271 | **0.5897** | 0.6096 | 0.8273 |

- 910 号文附件 4 写明的 0.8325，就是 2022 年的全国化石能源电力因子。
- 折标准煤 0.1229 kgce/kWh（当量值）与 GB/T 2589 原文一致。

**天然气**（生态环境部《企业温室气体排放核算与报告指南 钢铁行业》附表 A.1）

- 低位发热量 389.310 GJ/万Nm³，单位热值含碳量 0.01532 tC/GJ，碳氧化率 99%。
- 由此算得 55.61 tCO₂/TJ，即 **2.165 kgCO₂/m³**。
- 折标准煤：GB/T 2589 只给出区间 1.1000~1.3300。按同一低位发热量折算为 **1.3284 kgce/m³**，位于区间内，能耗与碳排放口径一致。

**柴油**（同上附表 A.1）

- 低位发热量 42.652 GJ/t，含碳量 0.02020 tC/GJ，碳氧化率 98%。
- 由此算得 72.59 tCO₂/TJ，即 **3.096 tCO₂/t**。
- 折标准煤 1.4571 kgce/kg（GB/T 2589，用于综合能耗）。

**热力**

- 化石能源热力 0.11 tCO₂/GJ，非化石热力计 0（910 号文附件 4）。
- 折标准煤 0.03412 kgce/MJ（GB/T 2589 当量值）。
- 企业按吨报蒸汽的，需要按热焓换算成 GJ。

**模型文档附录 B 的燃料因子**

- 大部分与 IPCC 2006 缺省值一致（汽油 69.3、柴油 74.1、燃料油 77.4、液化石油气 63.1）。
- 天然气 57.2 与生态环境部指南（55.61）和 IPCC（56.1）都对不上，来源不明，**不建议采用**。
- 这组因子已归为 `model_doc_apx_b` 口径保留。

## 8. 第一批导入模板（2026-10-20）

### 8.1 设计取舍：Excel 用宽表，数据库用长表

- **企业填表**：一行一家企业一个月，每种能源一列，最顺手。
- **数据库存储**：一行一家企业、一个月、一种能源，这样才通用。
- **两者之间**：由 `core.import_field_map` 负责“拆列”，每一列都配好对应的能源品种（或基础量）、单位和流向，导入时自动转换。

以后增加一种能源或一列指标，只需在映射表里加一行，再重新生成模板，不用改表结构。

### 8.2 模板清单

| 模板编码 | 文件 / 工作表 | 写入 | 列数 |
| --- | --- | --- | --- |
| `ENT_MONTHLY_ENERGY` | `templates/enterprise-monthly-energy_v1.xlsx` / 月度能耗 | `fact.energy_activity` | 18 |
| `ENT_ANNUAL_ECONOMIC` | `templates/enterprise-annual-economic_v1.xlsx` / 经济指标 | `fact.statistic_value`；是否规上、是否高企同时更新企业档案 | 12 |
| `ENT_ANNUAL_PRODUCTION` | `templates/enterprise-annual-economic_v1.xlsx` / 产品产量 | `fact.statistic_value`（按产品区分） | 10 |

### 8.3 关键规则

- **企业匹配**：先按统一社会信用代码，其次按企业名称。
- **电力拆分**：电网购电、绿电交易、直供非化石电力、光伏自用、光伏上网分列，对应不同的排放因子和流向。光伏上网电量写入 `flow = feed_in`。
- **数据来源下拉框**：计量表实测、系统导出（记为实测），手工台账、发票或结算单（记为手工）。
- **空单元格**：表示没有该能源，不写入。数值单元格只允许不小于 0 的数字。
- **重复上传**：同一企业同一期间再次上传时，新行替换旧行，旧行保留为历史。

### 8.4 模板生成

```bash
python scripts/generate_import_templates.py
```

- 脚本从数据库读取模板配置生成 Excel，保证表头与映射一致（已核对 40 列全部一致）。
- **本机默认的 Python 3.14.0a1（测试版）导入 numpy、openpyxl 时会崩溃**，请用 Anaconda 的 Python 3.13 运行：`~/anaconda3/python.exe scripts/generate_import_templates.py`。
