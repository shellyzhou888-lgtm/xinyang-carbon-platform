# PostgreSQL 连接与权限

## 开发连接

数据库位于服务器本机的 `127.0.0.1:5432`，本项目目标库名为 `greensystem`，应用角色为 `zyz`。用户最初提供的 `zyz` 是旧的目标库信息，已以最新指定的 `greensystem` 为准。参考项目连接的是同一服务器上的另一个库 `carbonsystem`，其库名不能直接复用。从开发电脑连接时，`127.0.0.1` 指开发电脑本身，因此使用 SSH 隧道：

```powershell
.\scripts\start-db-tunnel.ps1
```

该脚本用已授权的本机 SSH 私钥连接服务器 `2222` 端口，并将本机 `15432` 转发至服务器的 `127.0.0.1:5432`。也可以直接执行：

```powershell
ssh -p 2222 -i "$env:USERPROFILE\.ssh\id_ed25519" -N -L 127.0.0.1:15432:127.0.0.1:5432 administrator@218.197.118.49
```

首次配置时，在本机运行 `scripts/set-local-db-secrets.ps1` 并按提示输入两个账户的密码。脚本把应用连接串写入被 Git 忽略的项目 `.env`，管理员密码用 Windows DPAPI 加密后写入当前用户的 `%LOCALAPPDATA%\XinyangCarbonPlatform\postgres-password.dpapi`。两个文件均限制为当前用户、SYSTEM 和本机 Administrators 可访问；加密文件只能由当前 Windows 用户在本机解密。

保持隧道窗口运行，在另一个终端分别检查两个角色。检查脚本会读取本机凭据，缺少对应文件时才交互式询问密码：

```powershell
.\scripts\set-local-db-secrets.ps1
.\scripts\check-db-access.ps1 -User postgres
.\scripts\check-db-access.ps1 -User zyz
```

网站服务端从本机 `.env` 读取 `DATABASE_URL`，只使用 `zyz` 账户。不要把数据库密码放进浏览器端代码、版本库、更新日志或终端截图。重装 Windows 或更换登录用户后，重新运行配置脚本录入管理员密码。

数据库服务器目前不接受 PostgreSQL TLS 连接。2026-10-20 曾按参考项目的直连方式完成一次只读权限核对，随后已验证 SSH 公钥登录和隧道连接。持续开发使用 SSH 隧道，避免管理员查询和业务数据在公网链路上以明文传输。

## 角色分工

- `postgres`：数据库管理员，仅用于建库、角色授权、扩展安装和必要的管理操作。不作为网站日常运行账户。
- `zyz`：网站服务端连接账户。开发阶段就用该账户测试页面查询和写入，能及早发现权限与数据可见性问题。
- 如果将来有专门的迁移角色，用迁移角色创建和修改业务对象，并固定对象所有者和授权规则。

超级用户能越过普通权限检查和行级安全策略。用它开发页面会掩盖应用账户访问失败的问题。数据是否显示，通常取决于连接的数据库和 schema、表或视图的 `SELECT` 权限、行级安全策略，以及查询本身；对象由 `postgres` 创建，并不意味着 `zyz` 一定能读取。

## 后续授权

先用只读审计确认缺少哪些权限，再按实际功能授予数据库 `CONNECT`、schema `USAGE`、表或视图的 `SELECT`，以及确实需要的写入和序列权限。已有对象需要单独授权；未来对象可以由创建它们的角色配置 `ALTER DEFAULT PRIVILEGES`。该默认授权只影响之后创建的对象，且必须针对实际执行建表的角色配置。不要为解决页面显示问题而直接给应用账户超级用户权限。

数据库认证与授权完成后，应分别用 `postgres` 和 `zyz` 复测同一查询，再把页面运行连接固定为 `zyz`。这里的检查脚本只读取目录和权限，不更改业务数据。

## 2026-10-20 实际检查结果

- 客户端以本机私钥通过服务器 `2222` 端口免密登录；本机 `127.0.0.1:15432` 的数据库隧道已建立。
- `postgres` 和 `zyz` 均已通过该隧道成功连接到 `greensystem`；服务器版本为 PostgreSQL 17.5。
- 数据库所有者为 `greensystem` 角色；`postgres` 是超级用户，`zyz` 不是超级用户。
- `zyz` 对数据库有 `CONNECT` 和 `CREATE`，对 `public` schema 有 `USAGE` 和 `CREATE`。
- 当前 `public` 中没有业务表、视图或序列，因此还没有页面数据可供比较，也无需为已有业务对象补授权。
- 已有 `postgres` 在 `public` 中创建新表、序列、函数时授予 `zyz` 权限的默认授权设置。若由其他角色创建对象，需要检查该角色自己的默认授权，并对已创建对象另行授权。

这说明现在就可以用 `zyz` 作为网站服务端的开发连接账户。等业务对象创建后，应直接用 `zyz` 验证页面所需查询和写入；上线前再将建表、改表职责与网站运行账户分离，收紧 `CREATE` 等多余权限。

多个项目的分库方式和数据库 Agent 的角色设计见[多项目数据库与数据库 Agent 方案](多项目数据库与数据库Agent方案.md)。

## 2026-10-20 非 public schema 建表验证

`greensystem` 的数据库 ACL 已明确授予 `zyz` `CONNECT`、`TEMPORARY` 和 `CREATE`；其中数据库级 `CREATE` 允许它新建 schema。当前非系统 schema 只有 `public`，不存在其他已有 schema 需要补授权。

已用 `zyz` 在事务中执行 `CREATE SCHEMA codex_permission_probe`，随后在该 schema 中执行 `CREATE TABLE codex_permission_probe.check_table (id integer)`；两步均成功。事务已 `ROLLBACK`，并核对测试 schema 不再存在。**因此，`zyz` 现在就可以创建自己的业务 schema，并在其中建表，无需再补数据库授权。**

由 `zyz` 新建的 schema 默认归 `zyz` 所有。若今后要让它在*其他角色创建*的 schema 内建表，应针对那个具体 schema 授予 `USAGE, CREATE`，例如 `GRANT USAGE, CREATE ON SCHEMA business TO zyz;`。这不等同于允许它在所有未来 schema 中自动建表；登录、审计等敏感 schema 应按用途单独授权。
