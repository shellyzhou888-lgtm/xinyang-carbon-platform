# 语义目录、数据治理与语义增强查询

文档版本：v1.0（2026-10-20）

本文说明数据库 Agent 的第二版结构。思路参考了另一个项目的《数据库 Agent 设计方案》（多源异构可视化平台，第二章“数据基础模块”），但只取适合本项目的部分：本项目只有一个园区、约 40 张业务表，**不拆多个 Agent**，仍是一个数据库 Agent，外加一个无人值守的“治理检测”程序和一个网站审批页。

## 1. 要解决的三个问题

直接让大模型把问题翻译成 SQL（Text-to-SQL）有三类典型错误。对照参考方案表 7，本项目的对应做法如下：

| 问题 | 在本项目里的样子 | 解决机制 | 实现位置 |
| --- | --- | --- | --- |
| 模型只在提问时临时读表结构，不理解整库业务逻辑和表间关联 | 不知道 `flow = send_out` 要减去；不知道碳排放表里同一笔排放存了三个口径 | **语义目录**：提前写好表/字段的业务说明、粒度、口径陷阱、同义词、取值剖析、关联图、指标层和已验证问答对；提问时按关键词检索相关部分 | `semantic` schema；工具 `search_catalog`、`plan_joins`、`query_metric` |
| 脏数据、口径歧义、关联陷阱靠人工提前处理 | 某月用电只有中位数的 0.17 倍；产品产量定义单位“件”却存了 m³；视图把三个口径的碳排放相加 | **治理检测**：16 条 SQL 规则在每次导入/计算后自动运行，生成治理工单；大模型只读结果写说明；管理员在网站审批 | `semantic.check_def`、`governance_issue`；`npm run govern`；网站 `/admin` |
| 跨表、归因类问题生成错误 SQL 和口径幻觉 | 两张事实表按企业直接连接后求和，数值成倍放大 | **约束 + 校验**：指标层约束口径，关联图约束连接，复杂问题先拆分、用 WITH 先聚合再连接；SQL 先过执行计划校验、试执行，再交付；失败时把结构化原因交回模型，最多修复两次 | `sql-validate.ts`；`query_sql` |

## 2. 数据组织：专题与分层

| 维度 | 内容 |
| --- | --- |
| 处理阶段（schema） | `raw` 原始入湖 → `core` 主数据与字典 → `fact` 事实（版本化，`is_current`）→ `mart` 派生视图；`engine` 计算函数；`semantic` 语义目录与治理；`agent`/`audit` 日志 |
| 专题（`semantic.topic`） | 园区与企业、能源、碳排放、经济、资源环境、指标评价、参考字典、运行与治理。每张表在目录中登记所属专题和层级 |
| 规整约束 | 统计量统一用长表 `fact.statistic_value`（新指标 = `core.metric_def` 新增一行，不改表结构）；修正数据新增版本、不删除；每张可查询表都有业务说明，审核后回写数据库 `COMMENT`，人和模型读同一份说明 |

没有照搬参考方案的地方：不建向量库（目录只有几百条，关键词加 `pg_trgm` 相似度就够）；不用对象存储和 DataGrip 审批（审批放在本项目网站）；不建总管 Agent 和多个子 Agent。

## 3. 语义目录（AI 提前理解数据库）

| 组成 | 表 | 怎么来 |
| --- | --- | --- |
| 表说明 | `semantic.table_doc` | 21 个核心表/视图由人工起草（业务名称、说明、粒度、使用说明、口径陷阱、同义词）；其余取数据库注释；新表由 `refresh_catalog()` 自动登记 |
| 字段说明 | `semantic.column_doc` | 关键字段人工起草（含取值含义，如 flow、data_source、profile_code）；迁移文件中的行内注释和通用字段自动转入；剩余字段由治理运行让 AI 根据剖析结果起草，标为待审核 |
| 字段剖析 | `semantic.column_profile` | `profile_object()` 统计行数、空值、唯一值、最值、高频值；每次治理运行刷新 |
| 关联图 | `semantic.join_edge` | 外键自动登记为已批准；视图与无外键的逻辑关联（如碳排放 `profile_code` → 标准版本）人工声明；新关联需审核 |
| 指标层 | `semantic.v_metric` | 基础量的单位、聚合、来源和标准取数方式（`engine.metric_value`），以及引用它的已批准公式 |
| 已验证问答对 | `semantic.qa_pair` | Agent 成功执行的 SQL 自动成为候选，管理员批准后作为相似问题的示例 |

所有说明都有审核状态：`draft` 待审核、`approved` 已批准、`rejected` 驳回。Agent 能读到待审核的说明，但回答时会注明“待审核”。

## 4. 治理检测（无人值守）

**触发**：Agent 导入 Excel 或执行计算后，在后台自动运行一次；也可以运行 `npm run govern`（`--no-model` 只检测不调用模型），或在网站点“立即运行治理检测”。数据库触发器把导入批次入库、指标计算完成记为“发布事件”，下一次运行时一并处理。

**流程**：刷新目录与剖析 → 逐条执行检测规则（只读 SQL）→ 按指纹（规则 + 对象）开新工单、更新或重新打开旧工单、关闭已消失的问题 → 大模型为新工单写说明、影响和建议，并起草缺失的字段说明。

| 类别 | 规则 | 风险 |
| --- | --- | --- |
| 脏数据 | 月度能耗缺月；用量为中位数 4 倍以上或 1/4 以下；负值；导入晚于最近一次计算（批准即重算） | 中/高 |
| 口径歧义 | 统计单位与定义不一致；碳核算因子年份回退；企业资格真实记录与模拟记录冲突；法人名称未核实 | 中/低 |
| 关联陷阱 | 碳排放视图未区分口径；已批准关联边的键找不到对应记录 | 高/中 |
| 覆盖不足 | 某年模拟数据占一半以上；主版本指标公式未批准 | 中/低 |
| 目录 | 可查询表的字段缺说明（AI 起草）；已审核说明未回写数据库注释（批准即回写） | 中 |
| 洞察 | 园区能耗同比变化超过 10%；企业单位产值能耗超过园区平均 2 倍 | 低 |

**风险分级与执行**（对应参考方案表 14）：

| 风险 | 动作 | 执行方式 |
| --- | --- | --- |
| 低 | 生成工单、洞察卡片 | 自动 |
| 中 | 回写字段注释、重新计算 | 网站“批准并执行”，只开放这两类安全动作 |
| 高 | 修改指标口径、视图、关联、数据 | 网站只记录批准结论，修改由管理员用迁移脚本或导入完成 |

## 5. 语义增强查询的步骤

Agent 回答问题按以下顺序，能在前一步解决就不往后走（写在系统提示里）：

1. **固定工具**：能耗/碳排放汇总、指标状态、指标解释、因子、数据底账。
2. **指标层** `query_metric`：问基础量时直接按引擎口径取数（汇总范围、版本、口径、年度资格都已处理）；需要排名或比值时用 `ratio_of` 让程序计算并排序，模型不心算。
3. **检索目录** `search_catalog`：取相关表、字段说明与剖析、口径陷阱、合规关联、已验证示例、相关治理工单。
4. **规划** `plan_joins`：在关联图中找最短合规路径；路径先多对一再一对多时提示“先分别聚合再连接”。复杂问题拆成子问题，用 WITH 分步。
5. **校验** `query_sql`：PostgreSQL 先生成执行计划（`EXPLAIN VERBOSE`），同时完成语法、表和字段存在性检查；程序再读计划检查：
   - 有版本的表是否筛选了 `is_current`；
   - 碳排放是否限定或分组了 `profile_code`；
   - 每个连接条件是否在已批准的关联图中（两张事实表经同一维表直接连接会被拦下，先聚合再连接则放行）；
   - 是否在一对多连接后对“一”的一侧求和。
   - 对能源量求和时是否区分了 `flow`，含送出（send_out）时是否把它减去（v0.13.1 起，来自语音测试中模型把送出量加进综合能耗的实例）。
6. **试执行**：限定行数执行；空结果、预计行数过大给出提示。
7. **修复**：校验失败把错误代码、原因和修改建议交回模型，最多修复两次；仍不通过就向用户说明缺什么。
8. **沉淀**：成功的查询成为候选问答对，管理员批准后供以后复用。

为什么用执行计划而不是自己解析 SQL：视图会被展开成底层表，别名、隐式连接、CTE 内联都已由数据库解析好，规则只需读计划里的扫描、连接条件和聚合输出，不会因为写法不同而漏检。

## 6. 管理员审批（网站 `/admin`）

| 页签 | 做什么 |
| --- | --- |
| 治理工单 | 按状态、类别筛选；看说明、影响、建议和检测证据；批准（安全动作直接执行）、驳回（不再提示）、重新打开 |
| 语义目录 | 逐表审核业务说明；逐字段修改、批准、驳回；可一次批准本表全部已起草字段 |
| 问答对 | 修改问题表述后批准为示例，或驳回 |
| 关联图 | 审核新增的关联边 |

本机单用户部署，尚未加登录；审核人名称取环境变量 `ADMIN_NAME`。部署到多人使用前需要加登录和权限。

## 7. 权限变化

- `green_agent_ro`（模型写的 SQL 使用）新增可读 `fact` 与 `semantic`。此前只能读 `mart` 和 `core`，很多问题只能靠固定工具；现在有执行计划校验兜底，开放事实层。
- Agent 的写 SQL 工具不能修改 `semantic` 中任何内容：目录、关联图、问答对和工单的审核只能由管理员在网站完成。
- `semantic.apply_comment_sync` 以表属主身份执行，只能把**已批准**的说明写成 `core`/`fact`/`mart` 对象的注释。

## 8. 首次检测已知会出现的问题（迁移前用同样的 SQL 试跑）

- 万华生态 2021–2022 年有几个月电量为中位数的 0.17–0.24 倍（模拟数据的季节波动，需确认）。
- 产品产量 `PROD_OUTPUT` 定义单位为“件”，万华的 5 条记录为 m³：产品产量的单位应随产品变化，需调整定义。
- `mart.v_carbon_monthly` 把 GIP_2026、GIP_2024、ZCP_2025 三个口径相加：0022 已修正，规则保留以防再次出现。
- 2021–2025 年能源与统计数据模拟占比 100%；GIP_2026 有 4 个指标公式未批准；GIP_2026 碳核算有因子年份回退提示。
- 园区 2023 年综合能耗同比 +90.7%（今上、亚丹投产）；万华单位产值能耗约为园区平均的 4 倍。
